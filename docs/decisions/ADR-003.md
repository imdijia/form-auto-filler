# ADR-003: 把数据层抽象为 DataProvider，作为 v1 唯一必须提前做的设计投资

## Status

Accepted (2026-11-09)

## Background

用户明确：这是初版，后续可能增加「预设字段信息」（固定姓名、固定身份证），也可能需要 Excel/CSV 导入指定数据。基线方案 v0.3 的 3.2 节已定方向：初版不做预设，但必须留出扩展点。

风险很具体：如果 v1 把「按字段类型生成随机值」直接写进填充循环（`for (field of fields) { el.value = random(field.type) }`），后续加预设值时要同时改动识别层（字段要带预设键）、填充层（取值来源要分支）、配置层（新增配置结构与 UI）三处，且每次新增数据来源都要重跑三层的回归。这正是方案文档里说的「把生成器焊死在填充循环里」。

同时本项目还有两个约束放大了接口设计的重要性：

- 跨进程边界：`chrome.runtime.sendMessage` 只能传可 JSON 序列化的数据，接口里不能出现 `HTMLElement`、函数、`Map` 实例。
- 合法性约束：身份证校验位、出生日期与身份证 7-14 位一致、性别与第 17 位一致、手机号号段、枚举值必须来自页面字典。这些一致性不能由各生成器各自决定，必须有统一的上下文。

## Decision

**决策一：填充引擎只依赖一个接口，不认识任何具体 Provider。**

```ts
interface DataProvider {
  readonly id: string;
  getValue(field: FieldDescriptor, ctx: FillContext): string | Promise<string>;
}
```

- 参数只有纯数据 `FieldDescriptor` 与 `FillContext`；Provider 不 import DOM、不 import Vue、不 import `chrome.*`、不认识 Filler / FillPlanner。
- 返回值必须是**已满足** `field.constraints`（`maxLength` / `pattern` / `valueFormat` / `enumOptions`）的字符串；合法性由生成器负责，不由填充层补。
- `getValue` 允许返回 Promise，为后续 `CsvProvider` 异步读文件 / `PresetProvider` 异步读 storage 留出空间，不需要改接口。

**决策二：`FillContext` 承担跨字段一致性与可复现性。**

```ts
interface FillContext {
  sessionId: string;
  seed: number;
  siteKey: string;
  pageKey: string;
  generated: ReadonlyMap<FieldType, string>;
  locale: 'zh-CN';
  now: string;
}
```

`generated` 由执行层维护：`idCard` 一经生成，其 7-14 位出生日期与第 17 位性别奇偶即成为后续 `date` / `gender` 的依据。同一种子重放得到同一条记录，跨页面复用同一 `sessionId` 保证同一条记录在多页一致。这个逻辑集中在 `src/data/consistency.ts`，**不散落在 20 个生成器里**。

**决策三：Provider 由 `ProviderRegistry` 在入口装配期注入，支持优先级回落链。**

```ts
interface CompositeProvider extends DataProvider {
  chain: readonly DataProvider[];
}
interface ProviderRegistry {
  register(provider: DataProvider): void;
  resolve(ctx: FillContext): DataProvider;
}
```

版本路线：`RandomProvider`（v1）-> `PresetProvider`（v1.1，按字段类型 / 字段别名 / 页面+控件三级优先级读取，命中即用，未命中回落 Random）-> `CsvProvider`（v1.2）-> `CompositeProvider`（定义优先级链）。

**新增一个 Provider 只需三件事**：新增 `src/data/providers/<name>.ts`、在 `ProviderRegistry` 注册、options 页加一个表单。**识别层、填充层、执行层零改动**，第 6 章所有接口签名不变。

**决策四：`presets` 配置结构 v1 就写进 `rules.schema.json`，UI 先不暴露。**

```json
{
  "presets": {
    "global": { "personName": "", "idCard": "" },
    "bySite": {},
    "byPage": {}
  }
}
```

空值表示「未预设，用随机」，v1 引擎读到空值直接走 `RandomProvider`。`forceValue` 这个 `FieldOverride.action` 取值也在 schema 里预留，v1 不启用。

**决策五：敏感值约束写进契约，不靠自觉。**

预设值含身份证等敏感信息。`Logger` 接口禁止接收或写入身份证、手机号、预设值等原始值，只记字段名/类型/结果码；`exportJson()` 默认脱敏；不上传、不写日志。另如实说明：`chrome.storage.local` 是隔离存储而非加密存储，v1 不宣称「加密存储」，见 `ARCH-v1.md` 第 9 章。

## Consequences

**正面**

- 后续加预设/CSV 数据来源的改动面收敛到一个新文件 + 一次注册 + 一个表单，避免三层联动返工。
- 纯数据接口让 `RandomProvider` 与 20 类生成器可以脱离浏览器环境单测（无 DOM、无 `chrome.*`）。
- `FillContext.generated` 把「合法且自洽的一条记录」变成显式契约，而不是靠各生成器默契；直接对上基线方案 6.5 的难点。
- 配置 schema 提前落地，后续 UI 只是把已有字段暴露出来，不需要做数据迁移。

**负面 / 代价**

- v1 要多写一层接口、注册表与 `consistency.ts`，相对「直接在循环里调 random」多出约 1-2 天工作量。这是本 ADR 明确接受的投资。
- `getValue` 支持 Promise 意味着 `FillPlanner.plan` 必须异步；计划预览阶段就要把值取好并冻结，不能在执行时再取，否则预览与执行可能不一致。实现时必须遵守。
- `FillContext.generated` 是 `ReadonlyMap`，跨 `chrome.runtime.sendMessage` 边界时需要显式序列化/反序列化，不能整对象直接塞进消息。实现时按 `ARCH-v1.md` 6.1 的约束处理。
- 抽象本身有被绕过的风险：一旦出现「某个 Provider 直接操作 DOM」或「Filler 里 import 了某个具体 Provider」，投资即失效。5.2 节的门禁命令会把后者拦下，前者靠 code review + 纯逻辑层不 import `vue`/`chrome.*` 的约束防住。

**复核点**：第 12 章端到端验证第 7 条（同一种子两次填充，`idCard`/`date`/`gender` 一致且校验位正确）是决策二成立的关键断言。实现阶段需补一个「注入第二个 Provider 并断言检测/填充/执行层文件 diff 为空」的架构测试。

**v1.1 补充**：team-lead 裁决 3 重申 `DataProvider` 按方案 v0.3 3.2 保留，本 ADR 全部决策不变。另明确本地诊断计数（`faf.counters.v1`）与规则 / 配置（`faf.rules.v1`）、结果（`faf.lastPlan.v1` / `faf.lastResult.v1`）分键存储，`exportJson()` 不含计数、options 只展示聚合数字 + 一键清空。这不是 DataProvider 的职责，落在 ADR-004 决策四的零遥测边界里。
